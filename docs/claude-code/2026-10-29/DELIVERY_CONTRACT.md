# Delivery and Jira evidence contract

Each work order owns `docs/delivery/LAS-N/README.md`, `acceptance.md`, `manual-qa.md`, `results.json`, `jira-update.md` and appropriate logs/reports/media. These paths are deliverables to be produced by Claude, not evidence already generated by the handoff package.

## Git workflow

Keep main unchanged. Use a dedicated integration worktree/branch, and small issue branches such as `feat/LAS-11-pause-toggle`. Commit coherent slices with LAS keys; create small draft PRs targeting the integration branch where useful. After inspecting and testing your own issue commit, integrate it into the dedicated candidate branch, recording source SHA and integration SHA. This internal candidate integration is allowed; it is not approval to merge the final candidate into main. Do not silently merge unrelated contributors' unreviewed work. If only stacked PRs are feasible, document bases and provide a runnable integration candidate without pretending that the PRs were reviewed.

## Evidence

Record command, working directory, commit, environment, exit code, start/end time, pass/fail/skip counts and artifact paths. Report only executed checks as results. If a command fails and reruns pass, preserve initial failure, changes made and cause certainty. Keep screenshots/traces keyed by actual environment; do not turn Linux automation into a Mac or hardware-audio result.

Use deterministic synthetic audio in repo tests. For DSP, independently inspect samples/headers/true peaks/duration, preview/export parity and source hashes. For listening, record exact file/segment/alignment/constant gain/method and human verdict; otherwise NOT_RUN. For auth/storage, record direct API/storage negative tests, not only hidden UI controls.

## Jira update per key

1. Identify exact LAS key, branch/PR, application SHA and delivery directory.
2. State implemented/verified/research scope and each acceptance result with linked evidence.
3. Attach applicable HTML report ZIP, text/numerical report, trace/screenshot or research report to the matching issue; never delete historical attachments. Link immutable versioned repo files for large/code artifacts.
4. Include exact run/test commands, test data and manual QA instructions, with human actual result still Not Run.
5. State blockers, unsupported platforms, known failures and missing sign-off. Mark Ready for QA only when the relevant development criteria pass; map to an existing workflow state if available. Do not invent a Jira state or set Done/QA Done before the required user review.
6. If sync is unavailable, leave `jira-update.md` and list SYNC_PENDING in the rollup. A local comment draft is not a posted Jira update.

Do not mutate existing Test Plans/Test Cases to make evidence look complete. Reuse LAS-52/53/57, keep historical LAS-55/56 executions intact, and create new build-specific Test Executions only when actually running/reporting a new execution. Existing LAS-49 contains 24 responsive cases; reconcile IDs before creating duplicates.

## Aggregate candidate

Provide `docs/delivery/INDEX.md` with issue → sprint → branch/PR → candidate SHA → evidence → developer outcome → Gennady manual status. Include setup/seeds/test accounts without secrets, expected endpoints/ports, migration/rollback instructions and known limits. Every material belongs to a Jira key; shared infrastructure is referenced from each affected issue without pretending every issue owns the same implementation.
